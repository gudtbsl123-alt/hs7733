# 게임 자동 점검 (game-verify)

배포 전 관문이다. **PASS가 나오고 `content-critic`의 "반드시 고칠 것"이 0건일 때만** PR을 만든다.
사람이 보고 판단해야 하는 것(그림이 과학적으로 맞는지, 화면이 예쁜지)은 사진을 만들어 비평가에게 넘긴다. 기계로 잴 수 있는 것은 이 스크립트가 잰다.

## 1. 게임에 점검 창구 넣기 (모든 새 게임 필수)

게임 코드 맨 끝에 `window.__test`를 둔다. 게임 진행에는 쓰지 않고, 이 스크립트만 부른다. 이름·좌표는 그 게임에 맞게 채운다.

```js
/* 자동 점검 창구 (.claude/skills/game-verify) — 게임 진행에는 쓰지 않는다 */
window.__test = { version: 1, stageSize: [1280, 720],
  ui: { stage: '#game',            // 화면에 맞춰 커지고 작아지는 무대 요소
        name: '#nick',             // 이름 칸 (없으면 빼기)
        start: { x: 640, y: 600 }, // 시작 조작: 무대 좌표 {x,y} 또는 단추 선택자 '#bStart'
        pause: '#bPause', resume: '#bResume', mute: '#bSound',
        rotate: '#rotateHint', rotateOk: '#bRotOk',   // 세로 화면 안내와 '이대로 할래요'
        next: '#bNext' },          // 정답 뒤 다음 문제로 가는 단추 (없으면 빼기)
  isReady()  { /* 타이틀 연출이 끝나 첫 입력을 받을 수 있으면 true */ },
  quiet()    { /* 느린 화면 자동 저사양 전환·알림을 끈다 (빨리 감기 때문에 잘못 켜지지 않게) */ },
  items()    { /* [{ no, group, hint, exp, steps:[{ kind:'pick'|'multi'|'strike'|…, ask, opts, ans }] }] 게임 문항 데이터 그대로 */ },
  goto(no, step) { /* 그 문항·단계를 '답을 기다리는' 상태로 바로 띄운다 (다른 화면은 닫는다) */ },
  state()    { /* { scene:'title'|'play'|'result', no, step, phase:'ask'|'hint'|'ok', tries, cool(남은 대기 초), paused, muted } */ },
  targets()  { /* 지금 화면의 보기: [{ label, correct, x, y }] 무대 좌표(1280×720 기준). '결정' 단추는 { confirm:true } */ },
  start(nick){ /* 타이틀에서 첫 문제 전까지 실제 입력 없이 진행 (봇용) */ },
  botStep(mode) { /* 봇 한 걸음. mode: 'perfect' 모두 정답 · 'mixed' 가끔 틀림 · 'weak' 첫 시도는 늘 틀림. 지도·공연·보스 같은 문제 밖 구간도 여기서 처리 */ },
  result()   { /* 결과 화면 기록 { score, firstTry, wrongNote … } */ }
};
```

- `phase`: 답을 기다리면 `'ask'`, 틀려서 힌트가 떠 있으면 `'hint'`(대기 중이면 `cool>0`), 맞히면 `'ok'`.
- `targets()`의 좌표는 **실제로 그 자리를 누르면 그 보기가 눌리는 곳**이어야 한다(DOM 단추는 getBoundingClientRect, 캔버스 물체는 그린 위치).
- 3D·액션 게임처럼 보기가 움직이면 `targets()`를 부른 순간의 위치를 준다.
- 실제 예: `3학년 2학기 과학 소리의 성질(울림 밴드 월드 투어).html` 맨 끝.

## 2. 실행

```
NODE_PATH=/opt/node22/lib/node_modules node .claude/skills/game-verify/scripts/verify.js "<게임.html>" <결과 폴더> [all|static,content,play,devices]
```
- 결과 폴더는 scratchpad에 둔다(저장소에 올리지 않는다).
- 일부 기기만: `DEV=아이폰 …`, 원인 찾기: `DEBUG=1 …`.
- 3D(WebGL) 게임은 스크립트가 알아서 소프트웨어 WebGL로 연다. 2D 게임에는 켜지 않는다(큰 화면에서 너무 느려져 시험이 엇나감).
- 마지막 줄이 `PASS`여야 한다. `FAIL n건`이면 `report.txt`의 ✗를 하나씩 고치고 **다시 돌린다**. △는 확인만 한다.

## 3. 무엇을 보나 (✗가 나오는 경우)

| 구역 | 잡아내는 것 |
|---|---|
| static | 파일 이름 NFC 아님 · 이모지 · 바깥 주소(코드·실행 중 요청) · 불러올 때 오류 · `__test` 없음 |
| content | 정답이 보기에 없음 · 보기 중복 · 힌트·해설 없음 · 힌트가 정답을 그대로 말함 · goto가 다른 문항을 띄움 · **정답 위치가 매 판 섞이지도 않고 한쪽에 40% 넘게 몰림** · 글이 잘리거나 무대 밖으로 나감 |
| play | 모두 정답·섞어서·많이 틀리기 봇이 결과 화면까지 못 감 · 진행 중 오류 |
| devices (13종) | 무대가 화면에 꽉 차게 가운데로 안 맞음 · 세로 화면 안내 없음 · 길게 누르면 메뉴가 뜸 · **이름 쓰고 시작 조작이 안 됨(덮개가 클릭을 가림)** · 오답 탭에 힌트가 안 뜸 · 정답 탭이 안 먹힘(누른 곳의 요소를 함께 보고) · **오답들을 같은 순간에 누른 뒤 정답을 눌러 통과됨** · **보기가 나타나자마자 들어온 탭이 답이 됨(화면을 바꾼 탭 뒤 따라오는 클릭)** · 멈춤·소리 끄기 안 됨 |

## 4. 사람(비평가)이 볼 것 — 결과 폴더에 만들어 둔다

- `content/sheet_01.png …`: 모든 문항·단계 화면을 4장씩 모은 사진 + `content/items.json`(문항 글 전부)
  → **`content-critic` 서브에이전트**에게 사진 폴더, items.json, 학습지·단원 자료, 학년·과목·단원을 넘긴다. "반드시 고칠 것"을 모두 고치고 사진을 다시 만들어 한 번 더 받는다.
- `devices/<기기>.png`: 기기별 문제·정답 화면 → 직접 열어 글이 너무 작거나 가리는 곳이 없는지 본다.
- `play_<mode>_result.png`: 결과 화면 → 오답 노트·기록이 맞는지 본다.

## 5. 이 스크립트가 못 보는 것 (따로 확인)

- 그림이 교과 사실과 맞는지, 정답 단서가 그림에 드러나는지 → `content-critic`
- 그래픽 품질 → `art-critic`, 손맛 → `juice-critic`
- 실제 기기 속도: 시험용 브라우저는 그래픽 가속이 없어 큰 화면에서 느리다. 프레임 시간은 고치기 전·후를 같은 조건에서 비교하는 데만 쓰고, 저사양 모드는 CPU 4배 느리게(`Emulation.setCPUThrottlingRate`)로 따로 본다.
- 소리: 귀로 확인할 수 없으니 효과음이 호출되는지만 코드로 본다.
